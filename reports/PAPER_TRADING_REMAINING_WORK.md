## 2. 사용자가 직접 해야 하는 작업 (코드로 대신할 수 없음)

이 항목들은 계정 소유권·본인확인·자금이 필요해 Claude가 대신 실행할
수 없다 — 순서대로 진행 필요:

1. **거래소 계정 개설 + API 키 발급**: "별도 거래소"(기존 거래와 격리)
   계정을 새로 만들고, testnet API 키와 (나중에 라이브 전환 시) 실계좌
   API 키를 발급받아야 한다. 발급된 키는 반드시 `.env` 파일에만 넣고
   (기존 `.gitignore`에 이미 `.env` 포함돼 있음, 재확인 완료), 절대
   코드/커밋/로그에 남기지 않는다.
2. **$1,000 초기자본 입금**: 라이브 전환 시점에 필요(페이퍼는 testnet이라
   실자금 불필요). `config.yaml`의 `account.initial_equity_usd`는
   현재 플레이스홀더(10000)라 실제 입금액에 맞춰 갱신 필요.
3. **텔레그램 봇 생성**: BotFather로 봇 토큰 발급, 알림 받을 chat_id
   확인. 토큰은 `.env`에만.
4. **API 키 권한 설정**: 거래소 대시보드에서 해당 API 키의 권한을
   "거래만 허용, 출금 금지"로 제한(보안 표준 관행 — 코드가 대신할 수
   없는 계정 설정).
5. **최종 착수 승인**: 아래 30건 완료 후, 라이브 전환 여부를 사용자가
   최종 결정.

## 3. 30건 페이퍼 트레이딩 완료 판정 기준 (초안)

**주의: 이 기준은 승률·PF 같은 통계 기준이 아니다.** 그건 이미 G2/G3에서
과거 데이터로 확인했다(OFFICIAL_GATE_RESULT.md). 여기서 30건 동안 보는 건
**"실행 인프라가 설계대로 작동했는가"** 하나뿐이다 — 페이퍼 단계의
목적은 수익성 재검증이 아니라 실행 파이프라인의 신뢰성 검증이다.

| # | 항목 | 판정 방법 |
|---|---|---|
| 1 | 주문 체결 정확성 | 30건 전부 신호 발생→주문 제출 지연이 설계된 폴링 주기 이내, 체결가 괴리가 SPEC G4 기준(평균 ≤0.05%) 이내 |
| 2 | 스탑 배치 | 포지션 오픈 직후(설계된 타이밍 내) 스탑 주문이 거래소에 실제로 걸려있음을 매번 확인 — 예외 0건 |
| 3 | 상태 복구 | 30건 기간 중 최소 1회 프로세스를 의도적으로 재시작해 `recover_state()`가 실제 계좌 상태와 정확히 일치하는 결과를 냈는지 확인 |
| 4 | 알림 정확성 | 발생했어야 할 이벤트(진입/청산/리밸런스/CRITICAL) 전부 텔레그램으로 수신됨을 로그와 대조 확인, 불필요한 알림(스팸) 없음 |
| 5 | 예외 처리 | 처리되지 않은 예외로 인한 프로세스 크래시 0건. 발생한 모든 예외가 로깅되고 필요 시 텔레그램 발신됨(CLAUDE.md 원칙) |
| 6 | 자본 배분 | vol-parity 가중치(83.8:16.2)가 매 사이클 설계대로 적용됐는지 로그 대조 |
| 7 | 킬스위치 | 일일 손실한도 로직이 (자연 발생 시) 정상 작동하거나, 발생하지 않았다면 코드 리뷰로 로직 정확성 별도 확인 |

**판정**: 7개 항목 전부가 "예외 없이 설계대로 작동"해야 완료. 하나라도
설계와 다르게 동작하면 원인 규명 → 수정 → 그 심각성에 따라 30건 카운트를
이어갈지 리셋할지는 발생 시점에 사안별로 판단한다(경미한 로깅 누락 vs
스탑 미배치처럼 자금 손실 위험이 있는 결함은 다르게 취급해야 함 — 이번
문서에서 일괄 규칙을 미리 정하지 않는다, 실제 운영하며 다음 세션에서
사례 기반으로 결정).
