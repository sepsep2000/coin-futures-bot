## 2. 전략 로직 대비 정상성 검증

### 2.1 2a — 진입 정상, 청산은 조기 강제청산
- 진입(8개 자산, `k=19//4=4`, vol-parity 배분)은 이전 조사(2026-07-26, "설계상 정상")에서 이미 검증 완료 — 재확인 불요.
- 청산 사유는 전략의 "다음 주간 리밸런스"(정상이라면 2026-08-02T00:00 UTC)가 아니라 **킬스위치 강제청산**. 원래 계획보다 약 **5.75일 일찍** 청산됨.
- ⚠️ 미래 시점(08-02)의 실제 가격은 아직 발생하지 않아(현재 조사 시점 07-27) "계속 보유했다면 얼마였을지"는 사후에도 검증 불가능한 가정 — 추정치를 만들어 보고하지 않음(SPEC.md 원칙: 추정 금지).

### 2.2 filtered_trend ETH — 진입 정상, 청산 로직이 반복 오작동
`scheduler.py:434` 레짐 게이트(TREND) → `generate_trend_signals`(돈치안+확인봉) → `_momentum_agrees` 필터 → `position_size` 사이징까지 전부 코드 경로를 통과해야 진입 주문이 나가므로, 22:15:52 진입은 스켈레톤 우회나 임의 진입이 아니라 **정식 게이트를 통과한 정상 신호**다.

청산은 정상이 아니다. `src/backtest/engine.py:154` `_manage_trend_position()`은 `if not position.partial_taken:` 가드로 부분익절 중복 실행을 정확히 막고 있다(엔진 로직 자체는 결함 없음). 문제는 [scheduler.py:502-539](../src/live/scheduler.py:502) `_manage_open_filtered_trend_position()`이 **매 틱마다 DB에서 새로 읽은 position 객체**로 엔진을 호출한다는 점 — 만약 직전 틱에서 `partial_taken=True`가 DB에 저장되지 못했다면, 엔진은 매번 "아직 부분익절 전"이라고 오판하고 같은 조건을 또 충족시켜 재실행한다.

**근본 원인(확인됨)**: [scheduler.py:517](../src/live/scheduler.py:517)
```python
real_r_multiple = _current_r_multiple(position, result.avg_fill_price)  # None 가드 없음
```
[executor.py:150](../src/live/executor.py:150) `avg_price = order.get("average") or order.get("price")` — 시장가 주문은 `create_order()` 응답 시점에 `average`/`price`가 아직 채워지지 않는 경우(바이낸스/ccxt의 알려진 타이밍 특성: 시장가 체결 응답이 실제 체결정보보다 먼저 도착)가 있어 `None`이 반환될 수 있다(executor.py:154). 이때 `_current_r_multiple()`(engine.py:92, `mark_price - position.entry_price`)이 `None - float` 연산으로 `TypeError`를 던진다 — 로그의 `TypeError: unsupported operand type(s) for -: 'NoneType' and 'float'`와 정확히 일치.

이 예외는 **주문 체결(line 510, 이미 실거래소에 실행됨) 이후, `live_state.save_position()`(line 535, 상태 영속화) 이전**에 발생한다. 즉:
- 실제 거래소: 매도 체결됨 (되돌릴 수 없음)
- 로컬 DB: 상태 갱신 실패, 직전 값(qty=2.077, partial_taken=False) 그대로 유지

다음 틱에서 같은 포지션을 다시 읽어 같은 조건이 다시 참이 되므로 같은 매도가 재실행 — 이것이 8회 반복된 원인이다. 흥미롭게도 [scheduler.py:459](../src/live/scheduler.py:459) 진입 경로는 `result.avg_fill_price or entry_price`로 이미 None을 방어하고 있어, **동일 세션 내에서도 방어 코드가 있는 곳과 없는 곳이 나뉘어 있던 비일관성**이 사고를 만들었다.

### 2.3 킬스위치가 사고를 악화시킨 2차 결함
[scheduler.py:167](../src/live/scheduler.py:167) `_execute_kill_switch_liquidation()`은 `live_state.load_open_positions(db_path)` — **로컬(오염된) DB**를 읽어 청산 방향/수량을 결정한다. 거래소의 실제 포지션을 조회(`fetch_positions`)하지 않는다.

킬스위치 발동 시점(06:15:49) DB는 여전히 "롱 2.077"로 착각한 상태 → `close_direction="short"`, `qty=2.077`로 매도 주문 실행. 그러나 실제 거래소는 이미 반복 오청산으로 **순숏 -2.075**였으므로, 이 "청산" 주문은 포지션을 닫는 대신 **순숏을 -4.152로 배증**시켰다. "청산해야 할 안전장치"가 실제 거래소 상태를 확인하지 않고 로컬 상태만 믿었기 때문에 정반대 결과를 낳은 것 — 이 프로젝트에서 이미 여러 번 지적된 "공허한 성공/상태 불일치" 패턴과 본질이 같다.

미래(청산 이후)에 대한 추측은 하지 않되, **이미 지나간 실제 15분봉 데이터**를 사용해 "버그 없이 엔진 로직이 정상적으로(상태갱신 실패 없이) 매 틱 실행됐다면 어떻게 됐을지"를 실제 코드(`engine.py::_manage_trend_position`, 수정 없이 그대로)로 재현했다(가정치 아님, 코드 재실행 결과):

"버그가 더 이득이었다"고 해석하면 안 된다.

## 4. PnL 계산 검증 — "-$5,637.70"의 정체

### 4.1 결론: 이 수치는 NoneType 버그와 무관한, 별개의 선행 결함이다
텔레그램에 찍힌 `cumulative_pnl_usd`는 [scheduler.py:471](../src/live/scheduler.py:471)/[521](../src/live/scheduler.py:521)에서:
```python
cumulative_pnl_usd = total_equity - account_cfg["initial_equity_usd"]
```
`account_cfg["initial_equity_usd"]` = **config.yaml의 10804.0669** (2026-07-25 task j에서 "사용자가 알려준 현재 testnet 잔고"를 그대로 넣은 값 — G4 시작 시점의 실제 잔고가 아님, 당시에도 "설명되지 않은 괴리"로 플래그만 되고 미해결).

`equity_snapshots` 첫 행(G4 시작 직후, 2026-07-25T15:00:00) 실측: **total_equity_usd = $5,165.94304781** — 이것이 진짜 G4 시작 자본이다.

`-$5,637.70`이 정확히 어디서 나왔는지 `equity_snapshots`를 시간순 대조해 특정: **2026-07-26T22:15:00 스냅샷(total_equity=$5,166.3705547)** → `5166.3705547 - 10804.0669 = -5637.70` — **정확히 일치**. 이 시각은 ETH 진입 알림(22:15:52) 시점과 같다. 즉 이 수치는 **NoneType 크래시가 시작되기(23:15) 1시간 전, 최초의 정상 ETH 진입 알림에서 이미 나온 값**이다 — 사고와 무관하게, G4 시작부터 계속 잘못된 기준값으로 계산되고 있었다.

### 4.2 올바른 누적 PnL 재계산
```
올바른 기준선 (G4 시작 실측)  = $5,165.94304781
현재 실측 USDT 잔고(거래소 직접 조회) = $5,251.70403454
올바른 누적 PnL = 5251.70403454 - 5165.94304781 = +$85.76
```
구성: filtered_trend 실현분 +$27.78(수수료 반영) + 2a 실현분 -$9.54(수수료 반영) + ETH 미청산 숏 미실현 +$65.68 + 펀딩비(미분리, 소액 추정) ≈ +$85.76과 대략 일치. **봇은 실제로 손실 상태가 아니라 소폭 이익 상태다 — 다만 이 "이익"의 상당 부분(+$65.68)이 아직 청산되지 않은 리스크 포지션의 미실현분이라는 점은 4장의 경고와 동일하게 적용된다.**

### 4.3 두 값의 괴리 시작 시점
`total_equity - initial_equity_usd` 방식의 오류는 **G4 시작 순간부터 존재**했다(기준값 자체가 잘못됐으므로). 23:15 UTC NoneType 최초 발생과는 **인과관계가 없다** — 별개의, 더 오래된 결함(과거 조사에서 "괴리 있음, 범위 밖"으로 남겨졌던 바로 그 문제)이다.

**제외를 권고한다.** 이유:
- 2a 8건: 진입 로직은 정상(이미 검증됨)이지만, 청산은 전략 설계(주간 리밸런스)가 아닌 시스템 장애의 부산물이다. "정상 청산 사이클"로 셀 수 없다.
- filtered_trend 1건(명목상 "1건"이지만 실제 9개 주문): 진입은 정상이나, 청산 8회 중 8회가 전부 동일한 버그의 반복 산물이고, 마지막 킬스위치 주문은 청산이 아니라 **노출을 배증시킨 오작동**이다. "청산 로직이 정상 작동한 사례"로 셀 수 없음은 물론, 현재도 **포지션이 실제로 닫히지 않았다** — 판정 대상이 되려면 애초에 "종료된 사이클"이어야 하는데 이 트레이드는 아직 종료되지 않았다.

**대신 다음과 같이 분류할 것을 제안한다**:
- 이 9건(원인이 된 사고 전체)은 "정상 30건 판정 풀"에서 제외하고, **"장애로 인한 예외 처리 사례"로 별도 문서화** — 특히 **예외처리(NoneType 가드 누락)** 와 **킬스위치(로컬상태 신뢰 → 실거래소 미조회) 두 카테고리의 설계 결함 사례**로 명시적으로 남겨, 향후 해당 카테고리 판정 시 "이런 실패 모드가 실제로 발생했었다"는 근거로 활용.
- 2a의 진입 로직 자체(8건)는 이미 검증된 "정상 설계" 판정과는 별개로 유지해도 무방(청산 사유만 이례적).

### 6.2 즉시 조치가 필요한 사항 (우선순위 순)
1. **거래소에 ETH 숏 4.152개가 실제로 열려 있다** — 코드 수정 여부와 무관하게, 이 실제 시장 노출을 어떻게 처리할지 사용자가 직접 결정해야 한다(수동 청산 등). 제가 임의로 청산 주문을 넣지는 않았다.
2. 코드 수정 시 최소 2곳: (a) scheduler.py:517에 `result.avg_fill_price or <fallback>` 형태의 None 가드 추가, (b) `_execute_kill_switch_liquidation()`이 로컬 DB가 아니라 `exchange.fetch_positions()` 실측을 기준으로 청산 방향/수량을 결정하도록 변경 — 이번 사고처럼 "로컬 상태가 이미 틀린 상황"에서도 킬스위치가 실제로 안전망 역할을 하려면 (b)가 특히 중요.

4. `orders` 테이블의 `price` 컬럼이 시장가 주문에서 항상 NULL로 저장되는 문제(감사 추적 불가) — `save_order()` 호출 시 `limit_price`가 아니라 실제 체결 평균가를 저장하도록 수정 필요.
