# REBALANCE_ORDER_ANALYSIS.md — 2a 리밸런스 순서 마진 여유 시뮬레이션

LIVE_EXECUTION_ARCHITECTURE.md 6절 미결 사항("리밸런스 실행 순서")을
실행 전 확정한다. 결론이 먼저 나와야 `src/live/scheduler.py` STEP 2로
진행할 수 있다는 태스크 지시에 따라, 코드 구현 전 이 문서로 계산부터
끝낸다.

## 0. 전제 수치 (config.yaml 그대로, 재탐색 없음)

| 값 | 출처 |
|---|---|
| 총자본 E | $10,000 (`account.initial_equity_usd`) |
| filtered_trend 배분 w_ft | 0.8383017180188289 (`portfolio.weights.filtered_trend`) |
| 2a 배분 w_2a | 0.1616982819811711 (`portfolio.weights.2a`) |
| 레버리지 캡 L | 2 (`account.leverage`, isolated margin) |
| 2a 유니버스 | 20자산(`config/tickers.txt`), k = 20//4 = 5 (롱 5 + 숏 5 = 10슬롯) |
| 2a 슬롯당 가중치 | weight = 1/k = 0.2 |

**margin_mode: isolated** — Binance USDM은 심볼별로 격리마진 지갑을 따로
할당한다. 포지션을 열 때 그 순간 "가용잔고(available balance)"에서
필요 마진을 끌어온다 — 즉, 두 전략이 같은 순간에 신규 진입을 시도하면
같은 가용잔고 풀을 놓고 경쟁한다(이게 이번 시뮬레이션의 핵심 위험).

E_ft = E × w_ft = **$8,383.02**
E_2a = E × w_2a = **$1,616.98**
E_ft + E_2a = $10,000.00 (= E, 설계대로 정확히 100% — **버퍼 0%**라는 점이
이번 계산 전체의 출발점이다)

## 1. 각 다리의 최악 마진 요구량

**filtered_trend** (`src/risk.py::position_size`의 `max_leverage` 캡):
notional ≤ E_ft × L 이 되도록 캡을 걸므로, 격리마진 = notional / L ≤ E_ft.
→ **최악 마진 = E_ft = $8,383.02** (배분예산 100% 소진, 그 이상은 사이징
함수 자체가 막는다 — 이미 검증된 기존 로직, 재확인만 함).

**2a** (20자산 중 5롱+5숏, 슬롯당 비중 1/5):
- 롱 합계 notional = k × weight × E_2a = E_2a
- 숏 합계 notional = k × weight × E_2a = E_2a
- 총 notional(롱+숏) = 2 × E_2a
- 격리마진 = 총notional / L = **E_2a = $1,616.98** (평상시 정상 운용 중,
  10슬롯 전부 채워진 상태의 마진)

정상 운용 중(리밸런스가 진행 중이 아닐 때) 마진 합계 = E_ft + E_2a =
$10,000 = 자본의 정확히 100%. **이 시점에 이미 여유가 0이다** — 아래
리밸런스 전환 구간에서 순간적으로 마진 수요가 늘어나면 바로 초과한다.

## 2. 전환 구간(리밸런스 순간) — 청산 먼저 vs 신규진입 먼저

최악의 경우: 2a가 **20슬롯 전부 교체**(신규 5롱+5숏, 청산 5롱+5숏 —
n_changes=20, 실측 평균은 14.6/주지만 "최악의 경우" 요구사항이므로 전부
교체로 계산)하는 주간 경계 틱에, **같은 틱에 filtered_trend도 신규
진입 신호**를 낸다(최악의 경우, 두 조건 동시 발생 가정).

### (A) 청산 먼저 → 신규진입 나중

1. 2a 기존 10슬롯 청산 주문 제출 → 체결 확인 → 격리마진 즉시 해제.
   이 순간 2a 마진 사용량: $1,616.98 → **$0**.
2. 2a 신규 10슬롯 진입 → 격리마진 재사용: $0 → $1,616.98.
3. filtered_trend 신규 진입(있다면) → 최대 $8,383.02.

어느 순간을 봐도 동시에 필요한 마진 = (아직 안 닫힌 2a 포지션 마진) +
(이미 연 2a 포지션 마진) + (filtered_trend 마진) 중 **동시에 살아있는
것들의 합**뿐이다. 청산이 먼저 끝나므로 "옛 세대"와 "새 세대"가 동시에
살아있는 구간이 없다 — 순간 최대 마진 = **E_ft + E_2a = $10,000.00
(자본의 100%, 초과 없음)**.

### (B) 신규진입 먼저 → 청산 나중

1. 2a 신규 10슬롯 진입 → 격리마진 $1,616.98 추가 요청.
   **이 시점에 옛 10슬롯이 아직 청산되지 않았다** → 옛 세대 마진
   $1,616.98이 여전히 잡혀있는 채로 새 세대 마진 $1,616.98을 추가로
   요청 → 순간 2a 마진 사용량 = **$3,233.97**(2배, "이중 계상").
2. filtered_trend 신규 진입까지 겹치면: 순간 최대 마진 =
   E_ft + 2×E_2a = $8,383.02 + $3,233.97 = **$11,616.98**
   = 자본의 **116.2%** — **자본을 $1,616.98(16.2%) 초과**.

**결론: (B) 신규진입 먼저는 최악의 경우 가용잔고를 16.2% 초과해 주문
거부(마진 부족) 위험이 실측/계산상 명확하다. (A) 청산 먼저는 어떤
순간에도 자본의 100%를 넘지 않는다.**

## 3. 채택: 청산 먼저 → 신규진입 나중 (전략 무관, 틱 전체에 적용)

STEP 1 결론을 2a만이 아니라 **틱 전체의 일반 규칙**으로 확장한다 —
같은 틱에 filtered_trend의 청산(스탑 히트 등)과 2a의 청산이 섞여 있어도
마진 이중계상 위험은 없으므로(청산은 항상 마진을 풀 뿐 묶지 않음)
순서가 안전에 영향을 주지 않는다. 반대로 신규진입은 어느 전략 소속이든
전부 마진을 새로 묶으므로, **"모든 청산 먼저(전략 무관) → 모든
신규진입 나중(전략 무관)"**이 이 틱 처리의 불변식이다.
`src/live/scheduler.py`의 `_tick()`이 이 순서를 그대로 구현한다(2a
청산 → 2a 신규진입 → filtered_trend 처리, filtered_trend은 청산/스탑
체크가 신규진입 판단보다 먼저 오는 자체 내부 순서를 이미 갖고 있다 —
아래 4절 참조).

**청산 먼저의 단점(인지하고 감수)**: 청산~재진입 사이 짧은 시간
(초~수십 초, 폴링 주기 2초 기준) 동안 그 슬롯만큼 시장 노출이 없다 —
주간 리밸런스 시계에서 경제적으로 무시 가능한 수준(마진 초과로 인한
주문 거부 위험 대비 압도적으로 작은 비용)이라 이 결론을 바꾸지 않는다.

## 4. 부가 발견: ETH 심볼 충돌 (별도 위험, 이번 순서 결정과는 무관하지만 반드시 기록)

`config/tickers.txt`(2a 유니버스 20자산)에 **ETH/USDT:USDT가 포함되어
있다** — filtered_trend이 거래하는 바로 그 심볼이다. Binance USDM은
심볼당 격리마진 포지션이 원웨이 모드에서 하나뿐이라, 2a의 주간 랭킹이
ETH를 롱/숏 슬롯으로 선택하면 filtered_trend의 ETH 포지션과 **거래소
레벨에서 같은 포지션으로 넷팅**된다 — `state.py`는 (symbol, strategy)
복합키로 둘을 별개 행으로 저장하지만 거래소는 합산된 순포지션 하나만
본다. `recover_state()`의 대조 로직도 심볼 집합만 비교해 이 불일치를
잡아내지 못한다(같은 심볼이 양쪽에 다 있으면 "일치"로 보임).

이번 순서 결정(청산 먼저)과는 독립적인 문제이지만, 방치하면 두 전략의
포지션이 서로를 오염시킨다. **완전한 해결(헤지모드 전환 또는 심볼별
넷포지션 통합 회계)은 이번 태스크 범위 밖**(설계 변경 필요) — 대신
STEP 2 구현에서 **임시 완화책**을 적용한다: 2a의 라이브 리밸런싱은
ETH를 유니버스에서 제외한다(백테스트 `strategies/2a.py::run()`은
그대로 20자산 전체로 유지 — 게이트 통과 수치에 영향 없음, 라이브 실행
경로에만 적용되는 예외). 20자산 중 1개 제외가 2a의 통계적 성질에 주는
영향은 무시할 수 있는 수준으로 판단(재검증 없이 임시 조치로 채택,
사용자 검토 필요 — 최종 요약에 명시).

## 5. filtered_trend 자체 순서 (참고, 이미 기존 로직)

filtered_trend은 단일 심볼·단일 포지션이라 "동시에 여러 슬롯 청산/진입"
문제가 없다 — 매 틱 (a) 포지션이 있으면 관리(스탑/청산 체크)만, (b)
포지션이 없을 때만 신규진입 평가(`strategies/filtered_trend.py::run()`의
루프 구조 그대로, `if position is not None: ... continue` 뒤에 신규진입
분기). 즉 "청산 먼저 → 진입 나중"은 filtered_trend에는 이미 구조적으로
내재돼 있다 — 이번 결론과 자연히 일치, 별도 변경 불필요.

## 6. 결론 요약

| 순서 | 순간 최대 마진 | 자본 대비 | 판정 |
|---|---|---|---|
| 청산 먼저 → 신규진입 나중 | $10,000.00 | 100.0% | **초과 없음 — 채택** |
| 신규진입 먼저 → 청산 나중 | $11,616.98 | 116.2% | **16.2% 초과 — 기각** |

**채택: 청산 먼저 → 신규진입 나중(전략 무관, 틱 전체 불변식)**, 근거는
추정이 아니라 위 2절의 실측 계산(worst-case 20슬롯 전량 교체 + 동시
filtered_trend 진입 가정)이다. 부가로 ETH 심볼 충돌을 발견해 임시
완화책(2a 라이브 유니버스에서 ETH 제외)을 STEP 2 구현에 반영한다 —
근본 해결은 별도 후속 과제로 남긴다.

**추가 권고(이번 결론을 바꾸진 않지만 운영 안전판)**: 마진 버퍼가
정상 운용 중에도 0%라는 사실 자체가 취약하다 — 수수료/슬리피지가
이 계산에 없다. STEP 2 구현에서는 이론상 배분예산(E_ft/E_2a)만 믿지
않고 주문 직전 `exchange.fetch_balance()`로 실제 가용잔고를 조회해
사이징을 캡핑하는 안전판을 추가 권고(다음 절 구현에 반영).
