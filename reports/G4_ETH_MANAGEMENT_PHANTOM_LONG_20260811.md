## 4. 근본원인

[src/live/scheduler.py](src/live/scheduler.py) `_manage_open_filtered_trend_position()`의
청산 주문 제출부:
```python
result = executor.place_order(exec_exchange, db_path, FT_SYMBOL, close_direction, trade.qty)
```
1. **거래소 실측을 확인하지 않는다** — DB에 저장된 포지션 상태만 믿고
   "청산해야 한다"고 판단한다. 거래소 스탑이 자동 트리거된 것처럼
   DB와 실제 상태가 어긋난 틈이 생기면, 이미 없는 포지션을 "청산"하려는
   시도가 그대로 새 포지션을 만든다.
2. **`reduceOnly`가 없다** — 2026-08-11 오전 세션에서 `ensure_stop_placed()`
   의 대체청산(사고②/B 수정)과 킬스위치 청산(2026-07-27 사고 대응)에는
   이미 `reduceOnly=True`를 적용했는데, 이 일반 청산 경로는 그 개선이
   반영되지 않은 채 남아있었다.

## 5. 2026-07-27 킬스위치 사고와의 비교

| | 7/27 킬스위치 사고 | 이번(8/11~12) |
|---|---|---|
| 공통 원인 계열 | 로컬 상태(DB)가 거래소 실측과 어긋남 | 동일 |
| 어긋난 이유 | `avg_fill_price=None` → 예외로 상태 갱신 실패, 부분익절이 8회 반복 | 거래소 자동 스탑 트리거를 봇이 다음 틱까지 모름(설계상 필연적 지연) |
| 실제 피해 방식 | 반복 매도로 롱→숏 전환, 킬스위치가 배증 | 이미 청산된 포지션을 다시 "청산"하려다 반대 방향 신규진입 생성 |
| reduceOnly 적용 여부(사고 당시) | 없었음(이후 killswitch 청산·B수정 경로에 추가) | **이번 경로는 여전히 없음** — 미해결 |
| 발견 경위 | 정기 조사 중 발견 | 사용자가 계좌 미실현손익 이상치를 알아채고 질문 → 조사 중 발견 |

**공통 교훈**: "로컬 DB만 믿고 주문을 낸다"는 패턴이 발생 지점만 바뀐 채
계속 재발하고 있다. 이번엔 킬스위치나 신규진입 경로가 아니라 **정상
관리(청산) 경로**에서 처음 발견됐다 — 즉 이 문제가 국지적 버그가 아니라
"청산 주문을 내는 모든 경로에 공통된 설계 공백"일 가능성이 있다.
