`scripts/healthcheck.py`). SPEC.md 3/5/6절과 CLAUDE.md "오류 처리 표준"에
이미 정해진 원칙은 재결정하지 않고 그대로 인용·구체화한다.

## 0. 이미 SPEC.md/CLAUDE.md에 정해진 것 (재결정 안 함)

- **전략 = 순수함수, 백테스트와 라이브가 동일 함수 호출**(SPEC 3절). 이
  설계의 가장 중요한 제약 — 아래 전체가 이 원칙을 지키도록 짜여있다.
- **상태는 sqlite 영속화**(SPEC 3절) — 파일 vs SQLite를 다시 고르지 않는다.
- **오류 처리**: 네트워크/API 지수 백오프 3회 재시도 → 실패 시 CRITICAL
  알림. 주문 체결 확인은 주문 ID 폴링(fire-and-forget 금지). 포지션
  존재+스탑 부재 = 최우선 복구 대상(CLAUDE.md).
- **텔레그램 알림 최소 이벤트**(SPEC 5절): 진입/청산, CRITICAL(스탑
  배치 실패/API 연속 오류/킬스위치/프로세스 재시작), 일일 요약(09:00
  KST), 명령어(/status /pause /resume /close_all).
- **`mode: live`는 사용자만 config에서 바꾼다** — 코드 기본값은 절대
  live 아님(CLAUDE.md 규칙 5).

## 1. 주문 실행: REST vs WebSocket

**결정: REST(ccxt), WebSocket 안 씀.**

근거: filtered_trend는 15m 봉마감 트리거, 2a는 주간 리밸런스 — 둘 다
틱 단위 저지연이 전혀 필요 없다(SPEC 3절 "봉 마감 확정 데이터만 사용"
원칙과도 정합 — 틱을 볼 이유가 없다). WebSocket은 재연결·하트비트·
상태동기화 같은 복잡도만 추가하고 이 전략들엔 이득이 없다. 기존
`src/data/feed.py`가 이미 REST 기반 ccxt(`binanceusdm`)를 쓰고 있어
일관성도 맞다.

**주문 실패/부분체결 처리** (CLAUDE.md 기존 표준을 이 프로젝트의 두
전략에 구체적으로 적용):
- 주문 제출 → 즉시 주문 ID 확보 → 폴링으로 체결 확인(고정 간격, 예:
  2초, 최대 대기 시간 초과 시 미체결분 취소 시도).
- 네트워크/API 오류: 지수 백오프 3회 재시도. 3회 실패 시 CRITICAL
  알림 + 해당 사이클 스킵(다음 사이클에 재시도, 억지로 주문 강행 안 함).
  filtered_trend의 스탑 주문 배치 실패는 SPEC 3절 원칙상 **최우선
  복구 대상** — 포지션은 있는데 스탑이 없는 상태를 다른 어떤 처리보다
  먼저 해소해야 한다(CLAUDE.md).
- 부분체결: 체결된 수량만큼만 포지션에 반영, 미체결 잔량은 주문 상태
  폴링으로 계속 추적(취소 후 재주문 여부는 전략별로 다를 수 있음 —
  이번 설계에서는 정책만 명시, 실제 재주문 로직은 구현 단계에서 결정).
- 2a의 주간 리밸런스는 최대 20건(10 청산+10 신규, portfolio_2a_net_cost.py
  기준 실측 평균 14.6건/주)의 주문을 한 사이클에 낸다 — 이 중 일부만
  실패해도 전체를 롤백하지 않는다(부분 리밸런스 허용, 실패분은 다음
  사이클에 재시도 대상으로 상태에 기록).

## 2. 상태 영속화: SQLite 스키마 스케치

SPEC 3절이 이미 SQLite로 확정했으므로, 여기서는 스키마만 스케치한다
(실제 마이그레이션/구현은 골격 단계에서 TODO로 남김).

| 테이블 | 용도 |
|---|---|
| `positions` | 현재 보유 포지션(filtered_trend 심볼별 1개, 2a 자산별 롱/숏). symbol, strategy, direction, qty, entry_price, entry_time, current_stop 등 |
| `orders` | 제출된 주문과 상태(pending/filled/partial/cancelled/failed), 거래소 주문 ID, 재시도 횟수 |
| `equity_snapshots` | 주기적 자본 스냅샷(일별 손실한도 계산·일일 요약용) |
| `rebalance_log` | 2a의 주간 리밸런스 실행 이력(랭킹 스냅샷, 신규/청산 자산 목록) — filtered_trend의 `Trade`와 다른 스키마가 필요(portfolio_2a_net_trades.csv 구조 참고) |

**재시작 시 복구**: 프로세스 시작 시 (1) SQLite에서 `positions`/`orders`
로드 (2) 거래소 API로 실제 계좌 포지션·미체결주문 조회 (3) 둘을 대조해
불일치 시 CRITICAL 알림(자동으로 조용히 덮어쓰지 않는다 — 사람이
봐야 하는 상황). 이 3단계는 SPEC 3절 "프로세스 재시작 시 포지션/주문
복구"의 구체화다.

## 3. 스케줄링: filtered_trend(15m)와 2a(주간)를 하나의 루프에서

**결정: 단일 프로세스, 단일 루프, 매 15m 틱마다 두 조건을 확인.**

```
매 15m 틱:
  1. filtered_trend 체크 — 항상(매 틱마다 봉마감 데이터로 신호 평가)
  2. 2a 체크 — 이번 틱이 주간 리밸런스 시점(예: 매주 월요일 00:00 UTC,
     2a 백테스트의 pandas resample("W") 관례와 동일 경계)인지 확인,
     맞으면 리밸런스 실행
  3. 두 체크 모두 계좌 자본을 공유(vol-parity 배분은 "현재 총자본 ×
     가중치"로 매 사이클 재계산 — 배분 비율 자체는 config.yaml 고정,
     달러 금액만 그때그때 총자본에 연동)
```

**단일 루프를 택한 근거** (프로세스 분리 대안 대비):
- 두 전략이 **같은 계좌 자본을 공유**한다 — vol-parity 배분은 "현재
  총자본 × 가중치"로 매번 계산되므로, 두 프로세스가 따로 돌면 동시에
  자본을 읽고 포지션을 내는 레이스 컨디션이 생길 수 있다(예: 둘 다
  "자본 $1000"을 동시에 읽고 각자 자기 몫을 계산하는 중에 한쪽이 먼저
  포지션을 내 자본이 바뀌면 다른 쪽 계산이 낡은 값 기준이 됨).
- 일일 손실한도(kill switch)가 계좌 레벨이라 두 전략의 당일 손익을
  합산해서 봐야 한다 — 단일 프로세스면 자연스럽게 하나의 `daily_pnl`
  상태로 관리된다.
- 단점(인지하고 감수): 2a의 리밑런스 계산(20자산 순위 매기기)이 느리면
  그 틱에서 filtered_trend 처리가 지연될 수 있다 — 2a 계산은 실측상
  가볍다(주 1회, 20자산 랭킹은 초 단위) 실질적 문제 아님.

## 4. 알림: 최소 이벤트 (SPEC 5절 그대로 + 2다리 포트폴리오 확장분만 추가)

과도한 알림 지양 원칙 — **매 15m 틱마다 "신호 없음"을 알리지 않는다**,
상태가 실제로 바뀔 때만 보낸다.

| 이벤트 | 내용 | 우선순위 |
|---|---|---|
| filtered_trend 진입/청산 | 페어, 방향, 레짐, 수량, 가격, R배수, 누적 PnL(SPEC 5절 그대로) | 일반 |
| 2a 주간 리밸런스 실행 | 신규 진입/청산 자산 목록, 회전율, 이번 주 실현손익 | 일반(리밸런스 시점에만, 주 1회) |
| CRITICAL | 스탑 배치 실패, API 연속 오류(3회 재시도 소진), 킬스위치 발동, 프로세스 재시작, 재시작 시 상태 불일치 발견(2절) | 즉시 |
| 일일 요약(09:00 KST) | 당일 거래수·PnL·승률·현재 포지션·레짐 상태(SPEC 5절) — **포트폴리오 전체 + 다리별 분리 표기** 추가(2다리라 합산만 보면 어느 쪽이 잘하는지 안 보임) |
| 명령 | `/status`(포지션+자본+다리별 배분현황), `/pause`(신규진입 중단, 기존 포지션 관리는 계속), `/resume`, `/close_all`(전체 청산, 확인 프롬프트 필요) | 사용자 요청 시 |

## 5. 페이퍼/라이브 동일 코드 경로

**설계 원칙**: 거래소 API 호출부(주문 제출·조회·취소, 잔고 조회)만
`mode`(testnet/live)에 따라 분기하고, 그 위의 모든 로직(신호 계산,
포지션 사이징, 상태 관리, 알림)은 완전히 동일한 코드를 탄다 — 이미
`src/data/feed.py`의 `get_exchange(testnet: bool)`가 이 패턴을 쓰고
있다(SPEC 8절/DATA_REPORT.md 조사로 이미 검증된 패턴), `src/live/`도
동일 패턴을 그대로 재사용한다.

```
신호 계산(src/strategy/*, strategies/*)  <- 백테스트와 100% 동일 함수
        ↓
포지션 사이징(src/risk.py)               <- 백테스트와 100% 동일 함수
        ↓
주문 실행 계층(src/live/executor.py)     <- 여기만 testnet/live 분기
        ↓
ccxt 거래소 API(get_exchange(testnet=cfg["mode"]=="testnet"))
```

가짜(mock) 거래소를 만들지 않는다 — "페이퍼"는 실제 거래소의 testnet
엔드포인트에 실제로 주문을 내는 것이다(시뮬레이터가 아니라 실거래소
테스트넷). 이는 SPEC.md G4("testnet 실거래 100건")의 기존 정의와도
일치한다.
